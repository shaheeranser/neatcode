# Cross-Cutting Practices

Language-agnostic practices that keep code honest as it grows. Each one is something a god file
tends to violate, which is why it lives here rather than in a single adapter.

## Errors and validation

- **Wrap with context; never discard.** Add enough context to locate the failure (which operation,
  which input) while preserving the original error/cause so it can still be inspected.
- **Report all independent failures at once.** When several things can be wrong (a config, a batch
  of records), collect and return them together instead of failing on the first and making the
  caller iterate.
- **Expected bad input is an error, not a crash.** A malformed line, a missing file, or a failed
  request is handled. Reserve exceptions/panics for programming errors, and only at startup.
- **Validate at the boundary, trust inside.** Check user input, external APIs, and config where
  they enter the system; do not re-validate invariants deep inside trusted code.

## Dependencies

- **Standard library first.** Add a dependency only when it does something the standard library
  genuinely cannot, and write down the reason.
- **Every dependency is a maintenance and supply-chain cost.** Prefer a small local helper over a
  package for a one-off need.

## Injection and seams

- **Inject what you depend on.** Constructors/functions take their collaborators — clients, clocks,
  writers, config, loggers — as parameters. Reach for globals, singletons, or ambient I/O only at
  the outermost boundary.
- This is not only for tests: it is what makes behavior observable and replaceable, and it is the
  seam a refactor needs when code has become hard to test.

## Make uncertainty visible

- When structure or data cannot be resolved confidently, **preserve the source information and emit
  a warning or diagnostic** — do not silently drop a region, row, field, or file.
- A silent best-effort guess is worse than a loud, inspectable one; it hides bugs and erodes trust.

## One representation

- Carry the **richest structured form** of data through the system. Do not flatten it to a weaker
  representation (a string, markdown, a generic map) and then try to reconstruct the meaning later,
  unless that conversion is a deliberate compatibility boundary.
- Two parallel representations of the same thing drift; pick one and derive the other.

## Concurrency

- **Bound every queue and channel**, so a slow stage applies backpressure instead of growing memory
  without limit.
- **Guard shared mutable state** (mutex/lock); use atomics for counters that are only incremented.
- **Every goroutine/thread has an owner** that waits for it. Shutdown cancels work and waits for it
  to finish, and tests assert that nothing leaks.

## Tests are part of the design

- Write tests **with** the code, at the boundary that owns the behavior, not bolted on afterwards.
- **Deterministic and offline by default.** No live network, model, or external service in unit
  tests — stand in with fakes or test doubles. Fix clocks, seeds, and time.
- **Golden/snapshot files** for anything that parses or renders text (formatting, serialization,
  terminal output), regenerated by an explicit update flag so a diff is a reviewable artifact.
- **Table-driven** where a rule has several cases; **property-based** for pure logic with invariants.
  Avoid a handful of hand-picked inputs masquerading as property tests.
- Cover the **general rule**, not only the single input that motivated the change.
- Tests for a file live beside it, so a move carries its safety net along.

## Change hygiene

- Keep functional changes separate from unrelated cleanup; one concern per commit.
- Preserve the user's existing uncommitted work in the tree — never clobber it.
- Keep public APIs stable unless the task deliberately changes them.
- Do not commit generated or derived artifacts; keep local investigation outputs out of the
  published tree.
- Describe what was verified and call out what remains unresolved.
